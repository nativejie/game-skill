# 验证

## 一键检查（`validate.py`）

1. `Godot --headless --path <proj> --import --quit`（刷新全局类缓存）。
2. 对每个 `.gd` 跑 `--check-only`，出现 `SCRIPT ERROR` / `Parse Error` 就失败。
3. 跑无头规则测试，最后一行打印 `{"checks": N, "failures": [...], "passed": bool}`。
4. 主题检查 `scripts/check_theme.py`（缺 key、没填的占位；跨表重名只警告）。
5. 美术检查 `scripts/check_art.py <美术目录> <清单>`（没登记、没缩放、超大的图）。项目里已有未登记的旧图时，先补登记或缩放，再把它接进一键检查，免得一接进去就全红。

每改一块就跑一次。

## 规则测试怎么写

- `make_state(seed)`：读真实的 `game.json`，固定种子。`today` / `clock` 用可替换的 Callable，测试里注入固定时间（签到、限时外观要用）。
- 辅助函数：`run(state, 秒)`、`run_until(state, 事件)`（上限要大于一整轮）、`finish_event(state)`（按配置跑完当前事件）、`of_type(events, type)`。
- **不写死调参数值。** 修仙案例把事件时长拉长后，20 项测试失败，全是写死了「跑 46 秒」「跑 13 秒」。用 `finish_event` 和 `config.prepare_seconds + 1` 这样的写法，以后再调时长测试不用动。
- 覆盖：指令解析（包括容错写法和非法输入）、每种事件完整跑一遍、奖励数值、存档往返、旧版本存档读取、外观到期、BOSS 跨场、主题 key 覆盖、换主题等价。

## 文案快照（大重构前必做）

脚本：固定种子 → 6–8 名观众入座 → 给他们足够的材料和货币 → 跑两轮完整事件（约 2000 秒，步长 0.1）→ 每次进入等待和事件阶段，每人发一串指令（50 条左右，覆盖所有动作，包括非法名字、越界数字、重复签到）→ 记录每条回复的 `ok`、`message`、事件 JSON，以及所有 tick 事件、所有面板数据、所有静态名字（每个等级的称呼、每件外观的说明和获取方式…）。

修仙案例的快照有 17155 行，重构前后逐字 diff 为零。先跑两次确认快照本身是确定的。

脚本放临时目录，用完删掉；如果项目会频繁重构，可以留在 `tools/`。

## 随机数

- 规则层用自己的 `RandomNumberGenerator`，可固定种子。
- 模拟观众用全局随机数；重构时保持抽签数组的长度和顺序不变（例如把 `["强化", "升品", …].pick_random()` 改成 `Words.key(OPS.keys().pick_random())`，长度和顺序一致），否则后面所有随机结果都错开。

## 截图

- `--capture`：短时长跑一整轮，在每个事件的固定时刻截图（开始、激战、结算…），最后发几条查询指令截席位摘要。输出到工程外的 `evidence/` 目录。
- 对比改动前后：用 ffmpeg 并排拼图（`hstack`），看文字和排版。截图模式不固定种子时，皮肤和数字本来就不同；PSNR 这种逐像素指标没有意义。
- 窗口被遮挡时截图会停住，恢复瞬间连拍的几张是同一帧，要重拍。
- **按手机视角看**：把截图缩到约 386px 宽再目视，关键字号、遮挡、被截掉的小图标、空位残留状态逐张查（`art-pipeline.md`「手机视角验收」）。「有没有重叠」不够。

## 性能

- 原生窗口、窗口置顶、30 名模拟观众全员出手、整轮事件、不存档；不和录屏或其它 Godot 测试并行。
- 只统计事件期间的帧，排除截图帧；报告 P50、P99、最长帧、超过 33 ms 的帧数和发生在哪个事件第几秒。
- 修仙案例的参考水平：P99 约 18–19 ms，超过 33 ms 的帧 0–1 个。
- 被遮挡过的那一轮数据作废，在报告里说明。

## 洪峰压测

在性能测试之外单独做一次，条件同上（原生窗口、置顶、不并行）：

- 模拟每秒 300 条评论（其中约 10% 是有效指令，其余是聊天和写错的指令）+ 每秒 10 个礼物（含连击和重复 `msg_id`），持续 5 分钟，覆盖打怪和整屏事件。
- 报告：帧时间（P50 / P99 / 超过 33 ms 的帧）、队列最大积压、一条指令从进队到生效的最大延迟、礼物丢失数（必须为 0）、重复 `msg_id` 产生的重复效果数（必须为 0）。
- 积压持续上涨说明每帧处理上限太低或解析太慢；帧时间超标先看飘字数量和同屏上限。

## 平台消息回放

- 规则测试里加：同一 `msg_id` 的礼物发两次只结算一次；`count=10` 和拆成十条的礼物结果相同；未入座的人送礼会自动入座；满座时送礼会换掉闲置最久的位置。
- 有真实直播的 jsonl 记录后，用回放适配器跑一遍：不崩、礼物效果次数等于礼物条数、最终存档能正常读回。回放文件是真实观众数据，不进仓库。

## 演示录像

- `--demo`：固定种子，按剧本让两名展示观众依次发所有指令；BOSS 调成会在镜头里倒下；底部弹幕栏标「演示录像 · 模拟观众」。
- 录制：ffmpeg 录屏（macOS avfoundation），按引擎打印的窗口位置裁剪，转 720×1280、约 4 Mbps 的 mp4（3 分半约 100 MB）。录制时窗口无边框、置顶，不要遮挡它。

## 验收门槛

- 改动前先写死量化门槛（例如「首次升职 P50 不慢于 18 秒」「工资涨幅 ≤ 8%」「0 帧超过 33 ms」），和同种子的改动前结果对照。
- 任何一项没过：**如实报告、退回旧配置**，把取舍交给用户。不要自己调别的数值把线凑过去，也不要改测量方法让问题刚好避开（例如改截图剧本躲开卡顿）。
- 门槛是让用户看见取舍的触发器，不一定是否决：上班案例的一版排期首次升职慢了 23.5 秒、超线 5.5 秒，用户看过后认为换来的「10 分钟甩锅参与翻倍」更值，决定采用。
