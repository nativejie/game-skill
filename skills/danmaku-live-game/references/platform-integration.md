# 平台接入：把直播间的消息变成游戏输入

这一节讲结构和容易出错的地方，不讲某个平台的具体接口。抖音、快手、B站的开放接口、字段名、审核要求都会变，**接入时以平台当期的开放平台文档为准**。正式接入、开通权限、填密钥、上线审核，都要用户单独明确授权。

## 运行形态（以抖音直播小玩法为例的一般流程）

1. 主播在电脑上打开玩法程序，用直播伴侣（或其它推流工具）捕获游戏窗口推流。
2. 启动时平台给出这一场直播的凭证（房间、主播），玩法用它向平台开启「评论 / 礼物 / 点赞 / 粉丝团…」等消息的推送。
3. 观众在直播间发弹幕、送礼、点赞，平台把消息推给开发者的服务端（或直接给客户端，看平台方案），再转给游戏。
4. 下播时关闭推送任务。

游戏这边只关心第 3 步拿到的消息。中间那层叫**适配层**。

## 适配层：所有来源都变成同一种事件

```
抖音推送 ─┐
快手推送 ─┤
本地控制台 ─┼─> 适配层 ─> {"kind": …} ─> GameState.command / gift / like …
模拟观众 ─┤
录像回放 ─┘
```

统一后的事件（普通字典）：

```json
{"kind": "comment",  "msg_id": "…", "uid": "dy:openid", "nickname": "…", "avatar": "…", "ts": 1730000000.5, "text": "击退"}
{"kind": "gift",     "msg_id": "…", "uid": "dy:openid", "nickname": "…", "gift": "gift_wand", "count": 10, "price": 1}
{"kind": "like",     "msg_id": "…", "uid": "dy:openid", "nickname": "…", "count": 15}
{"kind": "follow",   "msg_id": "…", "uid": "dy:openid", "nickname": "…"}
{"kind": "fansclub", "msg_id": "…", "uid": "dy:openid", "nickname": "…", "level": 3}
```

- 规则层不知道消息从哪个平台来。换平台、加平台只写一个新适配器。
- **uid 带平台前缀**（`dy:` / `ks:` / `bili:`），模拟观众用 `sim:` / `local:`。平台给的用户 id 一般是按应用区分的 openid，不是抖音号，不能拿来跨应用对人。
- 平台的礼物 id 在适配层映射成游戏的礼物 id（`config/gifts.json`），规则只认游戏 id。礼物名是平台的，照用；效果描述按主题写。
- 头像只用来画席位，不存进存档；存档只存 uid、昵称（可更新）和进度。

## 消息不可靠：四件事必须处理

| 问题 | 表现 | 处理 |
|---|---|---|
| 重复 | 平台重推、网络重试，同一条礼物来两次 | 按 `msg_id` 去重（最近几分钟的集合）；礼物结算幂等 |
| 延迟 | 弹幕晚到几秒；礼物可能比之后的评论更晚 | 回应窗口留余量；不要假设不同类型消息的先后顺序 |
| 合并 / 拆分 | 连击礼物有时一条带 `count=10`，有时拆成十条；点赞往往一批一推 | 一律按 `count` 处理；画面效果在短时间窗口内合并成「×N」 |
| 断线 | 推送中断、主播网络抖动 | 心跳 + 自动重连；断线时画面角落提示「连接中」；重连后靠去重避免重复结算 |

## 礼物、点赞、关注怎么进规则

- 礼物 → `GameState.gift(uid, nickname, gift_id, count)`，查 `config/gifts.json` 得到效果 id 和强度，返回事件（例如 `{"type": "gift_fx", "fx": "thunder", "uid": …}`）。强度怎么定见 `gifts-and-compliance.md`。
- 没入座的人送礼：有空位就自动入座；满座时按「闲置最久的让位」规则换座（`live-stream-ux.md`「满座换座」）。否则新来送礼的人个人效果全白送。
- 点赞 → 全房间的累计进度（例如每 N 个赞触发一次全场小加成），个人只记一个计数用来上榜。
- 关注、加粉丝团 → 一次性的小奖励和身份标记（名牌颜色、徽章），不给数值碾压。

## 弹幕洪峰

大主播的直播间一秒几十上百条消息，绝大多数是聊天。

- 适配层收到消息先放进队列，规则层每帧最多处理一定条数（例如 50 条），剩下的下一帧。
- 解析失败的评论直接丢，只计数（给「未识别弹幕」统计用）。
- 同一个 uid 一秒内的重复指令合并；限制每人每秒有效指令数。
- 队列超长时先丢普通评论，**礼物永远不丢**。
- 画面层的飘字、伤害数字用对象池并设同屏上限，超出合并成「×N」。

压测方法见 `verification.md`「洪峰压测」。

## 本地开发与复现

- **本地适配器**：主播控制台和模拟观众都通过适配层发同样格式的事件，所以本地测通的逻辑上线不用改。
- **录像回放适配器**：把一场直播收到的统一事件按行写成 jsonl（昵称、头像可以脱敏），之后用回放适配器按原时间间隔重放。线上出 bug 时拿这份文件就能复现。
- 回放文件是真实观众数据，和模拟数据分目录存，不进仓库，清理要用户授权。

## 密钥与安全

- 应用密钥只放服务端或环境变量，不写进仓库，不打进发给主播的客户端。
- 平台推送如果带签名，服务端先验签再转发。
- 主播端只拿到这一场的临时凭证。
