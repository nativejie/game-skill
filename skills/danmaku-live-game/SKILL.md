# 直播弹幕互动游戏

这个 skill 提炼自抖音直播间的弹幕互动游戏（直播小玩法）：怎么拆竞品、怎么搭架构、怎么换皮、怎么定节奏和礼物、怎么开播和复盘。记录的是**做这类游戏时哪些事要先做、为什么，以及踩过的坑**。文中的数字和教训来自实际做过的两个案例：弹幕修仙（下称修仙案例，对标抖音头部弹幕修仙玩法）和上班社畜主题的原创玩法（下称上班案例），都是 Godot 4.6、竖屏 1080×1920。示例代码是 GDScript，方法和引擎无关。

## 先建立五个认知

1. **直播画面是所有观众共享的。** 这不是单机游戏。任何只和某一个观众有关的信息（背包、面板、详情）都不能占大画面，只能在这位观众的席位上方飘一两行；完整的个人面板属于以后的观众手机端。每加一个功能先问：这块画面是给谁看的？
2. **观众的输入只有一行文字，而且不可靠。** 指令要短（两个字的动词最好）、要能猜、要容错（多个关键词对应同一动作）；数字按当前事件解释。弹幕有几秒延迟、会洪峰、会重推，不做比反应速度的玩法。不发弹幕的人也要有收益（挂机、入座自动打 BOSS、点赞助力）。
3. **礼物只触发效果，不改规则。** 送礼的人要被看见，不送礼的人不能被碾压。不做押注、竞猜。
4. **主播是第一个用户。** 主播要能一个人开播、看得懂、找得到话说。游戏要主动制造口播点。
5. **会裂变成很多主题。** 同一套玩法以后会换成上班版、武侠版……所以从第一天起，规则代码里不写任何给人看的字。补做主题层的代价很大：修仙案例后来花了一整步，挪了 20 多个文件、几百处字符串。

## 核心做法（每条都附原因）

### 架构
- **规则 / 画面 / 主题三层分开。** `config/game.json`（数值、事件轮换、选用哪个主题）· `config/theme_<id>.json`（所有给人看的字）· `config/gifts.json`（礼物 → 效果 id 和强度）· `scripts/core/`（规则，只认 id 和数值，可无头测试）· `scripts/view/`（画面，只读状态、响应事件）· 一个组装层把规则事件分发给画面。原因：规则能脱离画面测试；模拟观众、控制台、平台接入走同一个入口；换皮只动配置。
- **规则只有一个入口**：`command(uid, 昵称, 弹幕)`、`gift(…)`、`like(…)` 和 `tick(delta)`，都返回事件列表（普通字典）。**事件带 id 不带文案**（`{"type": "loot", "item": "herb"}`），画面层按主题取名字。事件里带了文案，换皮时就会漏改。
- **平台消息先过适配层。** 抖音、控制台、模拟观众、录像回放都变成同一种统一事件；按 `msg_id` 去重、按 `count` 处理连击、队列限流、礼物永不丢。原因：平台消息会重复、延迟、合并、断线，规则层不该知道这些。
- **存档只存 id 和数值**，带 schema 版本号；每次加字段都让旧存档照常读取（给默认值）。
- **模拟数据和真实数据分开**：uid 带平台前缀（`dy:`），模拟观众带 `sim:` / `local:`，永远不当成真实观众数据。

### 主题层
- 加载器只有几个函数：`text(key, 参数)` / `name(表, id)` / `key(动作)` / `term(词)`。模板用 `{qi}`、`{item.herb}`、`{cmd.explore}` 引用别的词，加载时一次填好：改一个通用词，所有消息跟着变。新主题写 `"extends": "母版"`，只覆盖不同的部分。
- 弹幕解析**按动作查关键词**，动作 id 永远不变，一个动作可以有多个关键词。
- 美术先查 `assets/themes/<主题>/`，找不到再用通用目录，可以分批重画。
- 可直接复制的模板：`assets/words.gd`（Godot 加载器）、`assets/theme_template.json`（主题文件骨架）。检查脚本：`scripts/check_theme.py`（代码用到的 key 是否都在主题里、是否有没填上的占位）。

### 美术与风格
- **每个项目第一天写风格卡**：一句风格前缀（画风、配色、描边、比例，结尾固定「无文字…」）、抠图构图规则、视角、主要角色的固定外观、各类素材的尺寸档。只放一处（美术清单顶层），所有提示词从它拼，不论用哪个生图工具。格式和两个案例的风格卡见 `references/art-pipeline.md`，新项目另写，不混用。
- **图里不写字**，字一律走主题文件；提示词里的物品名和主题文件一致。
- **美术随功能一起做**：新功能当轮出图、接入、截图验收；生成失败如实报告，不悄悄用占位顶上。
- **每张图都走流程**：登记 → 生成 → 抠图缩放到尺寸档 → `scripts/check_art.py` → 状态预览拼图 → 截图。原图直接进游戏会拖慢首帧。
- **席位画成场景，状态用图表现**，只留几行必要的字；关键字在 1080 宽度下 ≥ 20px，缩到约 386px 宽验收。

### 节奏与数值
- **事件时长对照竞品录像定。** 修仙案例早期一轮 15 分钟、打怪每场只有 20 秒，用户指出竞品妖兽入侵每场好几分钟，才改成约 32 分钟一轮、打怪每场 3 分钟。打怪这类主事件应该占一轮时间的一半以上，等待和结算越短越好。
- 改时长前后跑 `python3 scripts/loop_length.py config/game.json`，看一轮多长、每个事件占多少。
- 数值好不好玩（第一次好事多久、最长空窗、保底、货币堆积）用 `casual-game-design` skill：它的 `scripts/pacing_sim.py` 几秒钟模拟几百个玩家几小时，`assets/example_spec.json` 就是修仙案例的数值。
- **奖励按「当前级所需的百分比」给**，不给固定数值。这样任何等级的感受都一样，调节奏只改一个比例。
- **先定每小时成长目标，再反推单次奖励。** 时长、怪的数量、奖励比例三者互相影响：改了一个，就用一小时实测把另外两个拉回目标。例子：打怪时长 ×9 以后，击杀数变成 5 倍、升级快了 2.6 倍，于是把击杀奖励从 15% 降到 4%。
- **难度按人数缩放**：怪的数量、BOSS 血量按在座人数和输出算，3 个人和 300 个人的直播间都要好玩。
- **免费不押。** 押资源的玩法容易让观众亏光就走，改成「参与就有奖、赢了奖更多」。
- 数值都写在配置里，策划案里标明哪些是从竞品读到的【参考】、哪些是我们定的【设计】。

### 礼物与合规
- **价位分档，强度封顶。** 1 抖币档必须有；效果强度换算成「免费玩家几小时收益」，随价格上升但封顶约 3 小时，再贵只加可见度和身份。改礼物表后跑 `python3 scripts/gift_ladder.py config/gifts.json`（模板 `assets/gifts_example.json`）。
- **连击合并、全屏效果排队**；送礼人署名；没入座的送礼人自动入座。
- **点赞、关注、粉丝团也有看得见的效果**，但不给数值碾压。
- 不押注、不竞猜、随机效果不能兑现、不写诱导打赏文案、不冒充真人；细则以平台当期规则为准（`references/gifts-and-compliance.md`）。

### 验证
- 规则测试**不绑死调参数值**：用「按配置跑完当前事件」这样的辅助函数，而不是写死「跑 46 秒」。
- **改数值必跑一小时无头实测**（`tools/soak.gd` 这种脚本，十几秒跑完一小时），报告每小时人均击杀、升层、货币、BOSS 何时倒下。实测脚本要模拟玩家的关键操作（例如自动「突破」），否则所有人卡在同一处，数据会整齐得可疑。
- **大重构前先录文案快照**：固定随机种子，跑完整轮事件，每个阶段发几十条指令（含非法的），把回复、事件、面板数据写成文本；改完逐字 diff。模拟观众的随机数调用顺序不能变。
- **接平台前做洪峰压测**：每秒几百条评论加礼物连击和重复 `msg_id`，看帧时间、队列积压、礼物丢失和重复结算（必须为 0）。
- 截图对比只比文字和排版（截图模式不固定种子时，数据本来就会不同）。
- 性能只在原生窗口测，窗口置顶，不和录屏并行；窗口被遮挡时 macOS 停止绘制，那段数据作废。报告写明条件（模拟观众数、是否存档）。

## 和用户合作

- 用户的决定写进工作根的 `AGENTS.md`（或 `CLAUDE.md`）「已确认方向」，带日期；冲突时以它为准。
- 有多个 Agent 轮流执行时，`docs/NEXT.md` 只写一步：具体改动、现成命令、量化门槛、不要做的事、没过线时退回并报告（不许调别的数凑线）、证据和文档的大小上限。执行完由规划者自己跑检查、核对数字、看截图再写下一步，不沿用执行者自评的「通过」。
- 每轮结束把下一步写进 `docs/NEXT.md`，用户中途提的需求做完单独记一节，写明还需要用户确认什么。
- 对齐竞品的是**风格和玩法**，名字、图片、界面素材都用自己的；平台礼物名是平台的，照用。
- 正式平台输入、付费、公网发布都需要用户单独明确授权；生图和平台密钥只从环境变量读。
